# Project Phoenix

A monocular clip-on heads-up display for eyeglasses: a 0.42" 72×40 OLED behind a
collimating lens and a 45° beamsplitter, driven by a Seeed XIAO nRF52840 that
talks to an iPhone over BLE.

**Everything here runs on a Mac with no hardware attached.** The display logic
lives in a portable, dependency-free C++17 library; the firmware and a desktop
simulator both consume it, so you can see exactly what the glasses would show
without owning them.

## See it work

```bash
cmake -B build && cmake --build build && ctest --test-dir build --output-on-failure
```

```bash
./build/sim/phoenix_sim --all && open sim/out/index.html
```

```bash
./firmware/build.sh
```

```bash
cd ios && xcodebuild -scheme Phoenix -destination 'platform=iOS Simulator,name=iPhone 15' build test
```

The second command is the one to run first if you only run one. It writes a
single self-contained HTML page with ten scenarios — boot, notifications,
an incoming call, turn-by-turn navigation, a streamed assistant reply, a
priority burst, a disconnect/re-bond cycle — each as a play/pause/step film
strip of real rendered frames with the triggering event labeled underneath.

Prerequisites: CMake ≥ 3.20 and a C++17 compiler for the core and simulator;
`arduino-cli` for the firmware (`brew install cmake arduino-cli`); Xcode for
the iOS app. `firmware/build.sh` installs the Seeed board package and U8g2 on
first run and needs network access. If `name=iPhone 15` is not a simulator you
have, either substitute one from `xcrun simctl list devices` or create it:
`xcrun simctl create "iPhone 15" com.apple.CoreSimulator.SimDeviceType.iPhone-15`.

## How the pieces talk

The iOS architecture is the unusual part. Notifications and the clock never
touch the companion app — the accessory subscribes to Apple's own services
directly over BLE:

```
NOTIFICATIONS:  iPhone --ANCS over BLE--> glasses          (no app involved)
CLOCK:          iPhone --CTS over BLE--> glasses           (no app involved)
ASSISTANT:      earbuds -> iPhone app (STT -> LLM) --custom BLE service--> glasses
```

The microcontroller holds both BLE roles on one connection: it advertises as a
peripheral serving the custom Phoenix service while simultaneously acting as a
GATT client consuming ANCS and CTS from the phone. ANCS requires bonding, so
pairing is requested on connect and bonds persist across reboots.

The app exists only for the voice path: your existing earbuds capture audio,
the phone runs speech-to-text and calls an LLM, the spoken reply goes back to
the earbuds, and only short text goes to the glass.

## Layout

```
core/        portable C++17 — framebuffer, fonts, layout, ANCS model,
             screens, screen manager, protocol codec. No Arduino, no nRF,
             no hardware headers, no external dependencies.
sim/         desktop harness: scenario scripts -> HTML film strips
firmware/    arduino-cli sketch for the XIAO nRF52840
ios/         SwiftUI companion app (CoreBluetooth + speech + LLM)
tools/       font/sprite generator and its readable ASCII-art sources
PROTOCOL.md  the custom BLE service: UUIDs, framing, message types
PLAN.md      build checklist, fully checked off
DECISIONS.md every judgement call, one line each
```

The prime directive: **all display logic is portable**. `core/` renders into a
plain 1bpp framebuffer packed in SSD1306 page order. The firmware pushes that
buffer to a real panel over I²C; the simulator renders it as inline SVG. There
is exactly one copy of the rendering code — `firmware/build.sh` syncs `core/`
into `firmware/lib/PhoenixCore` on every build (that copy is gitignored).

## What's tested, and how

`ctest` runs eight suites (~100 cases) with a hand-rolled, zero-dependency
harness:

- **Golden frames** — known inputs rendered and compared against committed
  ASCII art in `core/tests/golden/`. On failure both frames print side by side
  with differing rows marked. `PHOENIX_BLESS=1 ./build/core/tests/test_golden`
  rewrites them when a change is intentional.
- **Layout** — word wrap at boundary widths, hard breaks for over-long words,
  ellipsis truncation, a full marquee cycle, pager math.
- **Protocol fuzz** — every truncation prefix, a per-byte corruption sweep that
  proves later frames still decode, garbage interleaving, oversize lengths,
  arbitrary fragmentation invariance, and mutated streams. Also run under
  ASan/UBSan:
  ```bash
  cmake -B build-asan -DPHOENIX_SANITIZE=ON && cmake --build build-asan && ctest --test-dir build-asan
  ```
- **Screens and ANCS** — priority preemption and resume, teardown-before-enter
  ordering via a transition log, and add/modify/remove handling (a notification
  dismissed on the iPhone clears from the display).

The iOS side adds 39 XCTest cases: the Swift codec is validated byte-for-byte
against fixtures generated by the real C++ core, so the two implementations
cannot drift.

## Editing fonts and scenarios

Fonts and icons are ASCII art, not hex blobs. Edit `tools/fonts/*.txt` and
regenerate both the C++ and Swift tables:

```bash
python3 tools/gen_fonts.py
```

Scenarios are line-oriented scripts in `sim/scenarios/`. Add a file, rerun
`./build/sim/phoenix_sim --all`, and it appears in the page. To iterate on one:

```bash
./build/sim/phoenix_sim sim/scenarios/06_assistant_stream.txt
```

## iOS app without hardware

CoreBluetooth does not function in the iOS Simulator, so the app is built
around a `PhoenixTransport` protocol with two conformances: `BleTransport` for
real hardware and `FakeTransport`, an in-process virtual device that answers
like the firmware does. The Simulator uses the fake automatically, so the whole
app — push-to-talk, streaming reply, virtual glasses, protocol console — works
end to end with nothing connected.

### Where the LLM API key goes

The app works with **OpenAI or Google Gemini keys** — the provider is detected
from the key itself, so pasting one is all you do. With no key it degrades to
offline echo mode rather than failing.

| Key looks like | Provider | Default model |
|---|---|---|
| `sk-…` | OpenAI | `gpt-4o-mini` |
| `AIza…`, `AQ.…`, anything else | Gemini | `gemini-flash-latest` |

Both are called through the same OpenAI-format streaming endpoint (Gemini
exposes an OpenAI-compatibility URL), so there is one client and one SSE
parser for both.

**1. Runtime, no rebuild.** Launch the app → **Debug** tab → *LLM API key* →
paste (there's a clipboard button, since pasting into a secure field on the
Simulator is otherwise fiddly) → **Save to Keychain**. iOS will ask once for
permission to read the clipboard. The row above updates to e.g.
`Gemini · gemini-flash-latest`, and the next question hits the live model.
**Clear** removes it.

**2. Build-time.** Create `ios/Config/Secrets.xcconfig` — gitignored, and the
only file a key should ever go in:

```
PHOENIX_LLM_API_KEY = your-key-here
```

`ios/Config/Secrets.example.xcconfig` is a copyable template. Endpoint and
model are optional overrides; leave them unset and they follow the detected
provider. To point at a proxy, Azure, or a self-hosted OpenAI-compatible
server, set them explicitly (the `$()` in the template is an empty expansion
that stops `//` starting an xcconfig comment). Rebuild after editing.

The Keychain wins if both are configured.

## Known limitations

- **CoreBluetooth is unavailable in the iOS Simulator.** On-device testing
  requires a real iPhone; in the Simulator the app runs on `FakeTransport`.
- **iOS terminates background BLE permanently if the user force-quits the
  app.** It will not relaunch until manually reopened.
- **Free Apple developer provisioning expires after 7 days** and must be
  re-signed. The paid Developer Program removes this.
- **Connection interval, MTU, and PHY can only be requested by the accessory.**
  iOS decides. The firmware asks for a 247-byte MTU and takes what it gets; the
  wire format assumes nothing about fragment sizes.
- **The firmware is verified by compilation only.** No hardware was available,
  so `./firmware/build.sh` producing a clean build is the extent of the check —
  it has never been flashed or run on a panel.
- **Model ids drift.** Google retires dated ids (a pinned `gemini-2.5-flash`
  already 404s for new keys), which is why the defaults are moving aliases.
  If a call fails with a 404 naming a replacement, set `PHOENIX_LLM_MODEL`.
- **The renderer's glyph set is printable ASCII** plus a fallback box. Emoji and
  non-Latin text sanitize to that box (documented in PROTOCOL.md §6); they
  render harmlessly rather than crashing, but they do not display.
